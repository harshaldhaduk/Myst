# Building Myst

Read `AGENTS.md`, `PROJECT_CONTEXT.md`, `hub/DECISIONS.md`, `hub/PRD.md`, `hub/META_SUITE.md`, `hub/LOOP.md`, and every status file. The stack is Meta and Muse tools only; the product is mostly unbuilt, so the first job is learning what the platform allows.

## Before each slice

1. Run `scripts/hub-sync.sh`, then integrate with `git pull --rebase` or `git rebase origin/main` from a clean checkout. Read changed shared files before coding. Never force-push main.
2. Check `hub/status/` for active claims. Do not create another implementation of a claimed feature. Claim work over 20 minutes in your status file first.
3. Inspect the actual code and the platform docs. Separate existing behavior from the target in the PRD. Record substantial work in your status file, including cross-lane files.
4. Re-sync before another slice, before pushing, and at least every 15 minutes during long work. If another agent shares your checkout, never stage or discard its edits.

## Use Meta and Muse first

Before writing any capability:

1. Read `hub/META_SUITE.md` first, then the current Meta wearables developer docs and Muse docs for what you are about to use (search DAT docs with Meta's Wearables MCP, `search_dat_docs`). Note the glasses model, SDK version, firmware and permissions needed, and whether the feature is experimental.
2. Check the PRD capability table. If a row is unknown, resolving it comes before building on it.
3. Use the platform's implementation when it fits. If it is not offered, stop and raise it: the answer is a labeled mock, a redesign or roadmap, not an outside library, API or service.
4. Add only app-specific logic the platform cannot provide: consent and enrollment flow, memory content, response wording, uncertainty handling, demo reset.

## Integration boundaries

| Area | Rule |
|---|---|
| Profile/memory record and recognition result shapes | One shared definition once created; change it and all callers together and state the migration. |
| Response composer | Must pass through uncertainty handling; no spoken name or memory without a source record. |
| Demo data | Fictional unless the person consented; flagged as mock where scripted. |
| `face-demo/` | Retired (D10). Archive branch only; do not recreate, extend or import from it. |
| Dependencies | None from outside Meta's tooling without an accepted decision. Lockfiles are regenerated by the package manager, never hand-merged. |
| Secrets and personal data | Ignored `.env` only. Never commit tokens, photos, embeddings or memories. |

## Checks and shipping

Run whatever checks the platform's project template provides, plus any tests you add. A simulator or emulator proves wiring, not a real device. For anything about the glasses, record in your status what was run on the real hardware and what was not. Documentation-only changes need fact checks against the docs, not a device run.

Before pushing: sync and integrate, recheck affected behavior, update your own status, append proposed cross-lane or product decisions, stage only your files, and push without rewriting main. If a rebase conflicts, preserve the other lane's intent and reapply your change; ask when the intent is unclear.

Keep docs short: current facts, target behavior, integration constraints and remaining gaps. Do not reproduce chat history, invent delivery estimates, or turn proposed requirements into completed features.
